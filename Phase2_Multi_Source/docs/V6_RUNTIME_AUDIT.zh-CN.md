# v6 best16 续训：正确性和运行效率二次审核

日期：2026-11-04。运行命令见 [best16指南](V6_BEST16_RUN.zh-CN.md)。本轮代码包仍使用 `RIND_Phase2_Update.tar.gz`，不包含数据、缓存或权重；解压更新不会删除旧实验。

## 后续服务器OOM及针对性修复

服务器 `rind_v6_best16` 的日志在 `training_assignment` 的三输入 `einsum('btp,bsp,bp->bts', ...)` 报告一次8 GiB分配失败。当时该GPU另有进程占43.82 GiB，本进程约48.58 GiB，只剩2.57 GiB可用。这是已定位的内存分配错误，之前的CPU小缓存回归没有覆盖真实批量的中间张量规模。

未安装可选einsum路径优化器时，该写法可先形成 `[B,T,S,P]` 再沿像素维度P归约。现在统一替换为 `bmm(left * weight[:,None], right.transpose(1,2))`，先给一个输入加权，再收缩像素维度；临时量为 `[B,T,P]`，结果为 `[B,T,S]`。例如B=128、T=S=32、128×128窗口、float32时，前一写法的外积为8 GiB，后一写法的加权输入约256 MiB。该比例仅针对这项临时张量，不代表模型总显存降低32倍。数学目标和普通梯度保持一致，浮点归约顺序可产生舍入差异。

同类表达式已从v6训练/评价、历史v5、通用分层损失及失败诊断中移除，不依赖额外安装opt_einsum。新回归在禁用优化器的情况下复现旧四维外积，并检查新路径不产生四维张量、数值和梯度与显式求和一致。

批量探测此前只展开32层，而≥9层会开启检查点；这不一定覆盖关闭检查点的峰值。现在每个候选microbatch同时探测32层检查点路径和8层无检查点路径，以较高峰值验收。所有rank只在完整候选探测结束后汇总；任一rank或任一路径OOM，该microbatch均不采用。探测期间固定执行长度只用于显存压力测试，不做优化器更新，不读取教师剥离顺序；正式训练仍由学生自主计数。

`status` 在失败时显示首个Python traceback和具体异常，不再只给出C++栈尾。既有缓存、best16冻结快照和新实验的epoch断点都保留；重新启动会恢复已有 `last.pt`，没有新epoch断点则重新从已冻结的best16初始化。

本修复执行52个shell入口及343项全仓回归检查（326通过、17跳过），并补跑双进程Gloo及跨rank、多路径OOM一致性测试。尚未在本机H20执行，服务器仍需用更新后的双路径批量探测确定实际microbatch。共享卡恢复运行建议显式保留12 GiB余量，命令如下：

```bash
./run_implicit_masks_tmux.sh start all \
  --source-root outputs/masks_disentangled_v5_complex245746 \
  --expected-source-epoch 16 \
  --run-name masks_implicit_v6_best16 \

```

## 为什么匹配压缩仍是同一集合目标

设容量为S=32、当前真实层数为R、实际启用预测层数为Q。先将真实行和启用列排列在前，保留本批统一的 `L=max(R,Q)` 最大值。被删除的行列均为空；空行与空列匹配代价为零，任一真实层与未启用列的缺失代价不依赖该空列编号。任一最优完整分配都可把多余空行/列重新配对，保持总代价不变。因此L×L最优分配可扩展为S×S最优分配，既不删真实层也不删启用层。

容量32及原计数分类器不变。常见L=4时，原精确求解器两个固定循环的总迭代数由 `2×32²=2048` 减为 `2×4²=32`；这是该匹配子程序的循环量差异，**不是整轮训练加速64倍的测量结果**。若本批出现32层，回到完整32×32算法。

测试比较了最优代价、loss、唯一最优匹配下的梯度、缺失/额外层、任意启用槽编号、教师排列和满容量。完全同代价的多解仍可选不同最优匹配；不能承诺这种情况下梯度逐位一致。主要指标匹配先屏蔽未启用槽，评价文件记录 `enabled-shape-only-empty-padding-compacted-v2`；历史导出的匹配分数不能直接冒充新协议结果。

## 效率边界和验收

GPU自动选择检查近期利用率和空闲显存，不抢占其他进程。自动批量用各卡实际前向/反向、最坏32步展开和显存余量选择共同microbatch；在同卡数下保持有效全局batch。长展开使用检查点，短展开避免重算。

训练及例行模型选择不执行不参与两项loss的最终强度求解；正式推断和评价执行完整守恒检查。未验证的训练输出不会被标成已完成分解。CPU仍承担文件I/O、元数据、日志与调度；集合匹配数值运算和掩码解码留在张量所在设备。

本地没有H20/CUDA/NCCL，不能声称已经达到服务器峰值吞吐或不会遇到其他作业造成的显存竞争。交付前执行CPU全仓回归、独立双进程Gloo同步测试，以及最终tar干净解压、文件SHA和启动入口检查。服务器启动时还会运行真实缓存GPU解码对照、完整/压缩GPU匹配最优代价对照和自动批量显存探测；检查失败会在优化前停止。

最终tar干净解压后的全仓检查覆盖206个Python文件的语法、52个shell入口和339项测试（322通过、17因CUDA缺失或受限回环环境跳过）；另在允许回环的本地环境补跑3项双进程Gloo测试，均通过。CPU匹配微基准（B=16、S=32、L=4，预热后3次中位数）约为完整53.2ms、压缩0.882ms，最优代价一致；仅说明本地匹配子程序开销，不代表服务器或训练整轮加速倍数。

本机没有服务器上的完整大缓存和best16权重文件；已有回收结果及checkpoint元数据用于确认训练规模和版本。本轮数据/迁移回归使用真实格式的小缓存与测试权重，不能冒充本地已跑过345,746个真实窗口。服务器启动逻辑会核验实际大缓存的索引、文件长度和划分，并冻结、校验实际源权重；H20设备预检通过后才进入优化。
